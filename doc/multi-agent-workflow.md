# 多 Agent 协作开发工作流

本文档用于指导本项目在额度有限、需要频繁切换 Agent，或需要多个 Agent 并行开发时的协作。目标是让任何新 Agent 只依靠仓库中的文档、任务卡和 Git 状态就能继续工作，避免关键上下文只存在于聊天记录中。

## 1. 核心原则

1. **仓库是长期记忆。** 项目目标、技术决策、任务状态和交接信息必须写入仓库。
2. **一个任务对应一张任务卡。** 每个可独立验收的工作使用一个 `TASK-NNN` 编号，并在 `doc/tasks/` 中建立任务卡。
3. **一个写入者对应一个工作区。** 同一时间只允许一个 Agent 写同一个工作区；并行写代码时必须使用不同的 Git worktree 和分支。
4. **先读后写。** 新 Agent 开始前必须阅读 `AGENTS.md`、`doc/plan.md` 和当前任务卡，并检查 Git 状态。
5. **小步提交、明确交接。** Agent 停止前要留下可恢复的安全检查点。
6. **完成以验收标准为准。** 代码写完不等于任务完成；验收、验证、审查和集成都完成后才能标记 `done`。
7. **协调者管理共享文件。** 根配置、锁文件、共享协议、迁移文件和项目计划等高冲突文件由协调者统一修改或集成。

## 2. 协作信息存放位置

| 文件或机制 | 作用 | 主要维护者 |
| --- | --- | --- |
| `AGENTS.md` | 全仓库长期有效的开发规则 | 协调者 |
| `doc/plan.md` | 产品目标、版本范围、架构和关键决策 | 协调者 |
| `doc/tasks/README.md` | 任务索引、状态定义和并行约束 | 协调者 |
| `doc/tasks/NNN-*.md` | 单个任务的范围、进度、验证和交接 | 当前负责人 |
| Git 分支 | 隔离每个实现任务的改动 | 当前负责人 |
| Git worktree | 隔离并行写入者的工作目录 | 协调者 |
| Git 提交 | 保存可审查、可回退的检查点 | 当前负责人 |

信息优先级如下：

1. 用户当前明确给出的要求；
2. 当前任务卡中的范围和验收标准；
3. `doc/plan.md` 中已确认的产品与架构决策；
4. `AGENTS.md` 中的仓库规则；
5. Agent 自己的判断。

如果它们互相冲突，Agent 应停止扩大冲突范围，在任务卡中记录冲突，并由协调者统一修正文档。

## 3. 工作目录边界

项目主工作目录：

```text
/home/lzs/Projects/pi
```

PI 源码参考目录：

```text
/home/lzs/Projects/pi/pi
```

`pi/` 只用于阅读和检索 PI SDK 的实现，不属于本项目的实现目录。Agent 不得在其中写入代码、格式化文件或提交改动。

## 4. 角色划分

一个 Agent 可以在不同阶段承担不同角色，但每次工作都必须明确当前角色。

### 4.1 协调者与集成者

负责：

- 把产品计划拆成可独立验收的任务；
- 分配任务编号、分支和 worktree；
- 判断哪些任务能够并行；
- 管理共享文件和高冲突文件；
- 处理跨任务的接口与架构冲突；
- 审查并集成已经完成的改动；
- 更新任务索引和项目进度。

协调者不应把多个互相依赖的大目标塞进同一张任务卡。

### 4.2 实现 Agent

负责：

- 只处理被分配的任务；
- 开始前复述任务边界；
- 遵守当前任务的文件所有权；
- 实现代码并运行必要验证；
- 更新任务卡的进度、决策、验证和交接信息；
- 在安全检查点提交改动。

如果发现必须修改共享协议或根配置，应先在任务卡中记录需求，再交给协调者处理。

### 4.3 调研 Agent

默认只读，适合：

- 阅读 PI SDK 源码；
- 分析参考性 Agent 工作台的模块与行为；
- 比较技术方案；
- 查找相关接口、测试或示例；
- 输出结构化结论和实现建议。

调研结果应写入当前任务卡或任务指定的调研文档。没有明确授权时不修改实现文件。

### 4.4 审查 Agent

负责检查：

- 是否满足任务卡的验收标准；
- 是否存在范围外改动；
- 正确性、并发、安全、兼容性和可维护性；
- 验证是否足以支持结论；
- 文档、类型和实现是否一致。

审查结论按严重程度列出，并注明文件和位置。没有发现问题时，也要说明审查范围和仍未覆盖的风险。

### 4.5 文档 Agent

负责整理已经确认的信息，例如同步架构文档、补充使用示例、维护任务索引和统一术语。文档 Agent 不替代协调者做尚未确认的产品或架构决策。

## 5. TASK-NNN 的含义与命名

`TASK-NNN` 是任务编号占位符：

- `TASK` 表示一项可跟踪工作；
- `NNN` 表示三位顺序编号；
- 当前已有的第一个任务是 `TASK-001`；
- 后续依次使用 `TASK-002`、`TASK-003`。

统一命名方式：

| 对象 | 格式 | 示例 |
| --- | --- | --- |
| 任务编号 | `TASK-NNN` | `TASK-001` |
| 任务卡 | `doc/tasks/NNN-short-name.md` | `doc/tasks/001-pi-sdk-spike.md` |
| 分支 | `task/NNN-short-name` | `task/001-pi-sdk-spike` |
| worktree | `../pi-task-NNN` | `../pi-task-001` |
| 提交主题 | `type(scope): message` | `feat(runtime): add PI SDK probe` |
| 提交正文 | 引用任务号 | `Refs: TASK-001` |

提示词中的 `TASK-NNN` 必须替换成实际编号，不能把占位符原样当作任务名。

## 6. 任务拆分标准

一张合格的任务卡应满足：

- 有一个可以清楚描述的结果；
- 有明确的范围内和范围外事项；
- 不依赖聊天历史也能理解；
- 有可执行的验收标准；
- 有验证命令或人工检查方式；
- 最好只涉及一个主要模块；
- 完成后可以独立审查和提交。

以下情况通常应拆分任务：

- 同时包含协议设计、后端实现和前端实现；
- 需要多人同时修改同一组文件；
- 验收标准包含多个互不相关的结果；
- 某一部分必须先完成，另一部分才能开始；
- 调研结论可能完全改变实现方案。

有不确定性时，先建立调研或基础任务，再建立后续实现任务。

## 7. 任务状态生命周期

```text
backlog → in_progress → review → done
                ↓
              blocked
```

### 7.1 `backlog`

任务已建立但尚未开始。进入 `in_progress` 前至少需要：目标、范围、验收标准、依赖和执行角色。

### 7.2 `in_progress`

某个 Agent 正在实现。任务卡应持续记录：

- 已完成内容；
- 当前工作；
- 新发现的约束；
- 已做出的局部决策；
- 尚未验证的假设。

### 7.3 `blocked`

存在当前 Agent 无法消除的具体阻塞，例如上游任务未完成、需要用户决定互斥方向、缺少必须的外部资源，或共享协议尚未确认。

任务卡必须写清阻塞原因、已尝试动作，以及解除阻塞需要谁做什么。工作困难不等于阻塞；只要还有可独立推进的工作，就应继续。

### 7.4 `review`

实现 Agent 已满足验收标准并提供验证证据。进入审查前应具备：

- 完整实现；
- 工作区中没有不明来源的改动；
- 任务要求的测试、类型检查、lint 或人工验证已经完成；
- 任务卡记录了验证命令与结果；
- 已列出剩余风险；
- 已形成可审查的 Git 提交。

### 7.5 `done`

审查问题已经解决，协调者已集成改动，并确认任务索引或计划已经更新。只有协调者或明确承担集成职责的 Agent 才将状态改成 `done`。

## 8. 创建新任务

1. 从 `doc/plan.md` 选择一个边界清楚、尚未实现的结果。
2. 在 `doc/tasks/README.md` 中找到下一个未使用编号。
3. 复制 `doc/tasks/TEMPLATE.md` 创建任务卡。
4. 填写目标、背景、范围、验收标准、依赖、风险和验证计划。
5. 在任务索引中加入任务，状态设为 `backlog`。
6. 判断是否会修改共享文件，以及能否与其他任务并行。
7. 分配给 Agent 时，将状态改为 `in_progress`。

先建立任务卡，再开始实现，避免 Agent 写完代码后再猜目标。

## 9. Agent 开始任务的标准流程

每个新 Agent 都应：

1. 阅读根目录 `AGENTS.md`。
2. 阅读 `doc/plan.md` 中与任务相关的部分。
3. 阅读 `doc/tasks/README.md`。
4. 阅读当前任务卡全文。
5. 检查所在路径、当前分支和 Git 状态。
6. 检查上一个交接点和未提交改动。
7. 简短复述目标、范围、验收标准和下一步。
8. 从任务卡中的“下一步”继续，不重复已经完成并验证的工作。

建议检查命令：

```bash
pwd
git branch --show-current
git status --short
git diff --stat
git log --oneline -5
```

工作区已有改动时，新 Agent 必须先理解来源，不能直接覆盖、回退或格式化整个仓库。

## 10. 顺序接力：额度有限时切换 Agent

额度有限时，默认使用顺序接力：一个 Agent 停止写入并完成交接后，下一个 Agent 在同一 worktree 中继续。

### 10.1 旧 Agent 的交接动作

1. 停在可以解释和恢复的安全检查点。
2. 运行当前阶段能够运行的验证。
3. 更新任务卡中的已完成、未完成、关键决策、修改文件、验证结果、风险和下一步。
4. 提交可以独立成立的改动。
5. 如果不能提交，说明未提交文件、原因以及是否可以安全继续。
6. 明确表示已经停止写入。

### 10.2 新 Agent 的接管动作

1. 按第 9 节完成启动检查。
2. 对比任务卡、Git 日志、工作区差异和实际代码。
3. 确认旧 Agent 已停止写入。
4. 先处理明显不一致，再继续任务。
5. 延续同一任务编号，不重复建立新任务。
6. 持续更新同一张任务卡。

### 10.3 是否可以复用同一工作区

只有旧 Agent 已经停止时，新 Agent 才能复用同一 worktree。两个仍在运行的 Agent 不能同时写入同一目录，即使它们计划修改不同文件。

## 11. 并行开发的适用条件

只有满足下列条件才适合并行：

- 任务之间没有未完成的强依赖；
- 主要修改文件不重叠；
- 不会同时修改根配置、锁文件、共享协议或迁移文件；
- 每个任务都有独立验收标准；
- 协调者能在合并前统一处理接口差异。

适合并行的例子：

- 一个 Agent 只读调研 PI SDK，另一个整理任务设计；
- 一个 Agent 实现独立后端模块，另一个完善不依赖它的文档；
- 一个 Agent 实现当前任务，另一个审查已提交的上一任务。

不适合并行的例子：

- 两个 Agent 同时定义同一个事件协议；
- 两个 Agent 同时修改根 `package.json` 或 lockfile；
- 前端依赖尚未确定的后端接口；
- 一个 Agent 重构另一个 Agent 即将修改的核心模块。

## 12. 创建并行 worktree

### 12.1 当前仓库的前置条件

当前根仓库已经初始化并位于 `main` 分支，但尚无初始提交。Git worktree 需要可引用的基准提交，因此必须先由协调者完成初始提交，之后才能创建并行工作区。

### 12.2 创建任务 worktree

初始提交完成后，协调者可以在项目根目录执行：

```bash
git worktree add ../pi-task-002 -b task/002-event-protocol main
git worktree add ../pi-task-003 -b task/003-session-storage main
git worktree list
```

目录与分支关系：

```text
/home/lzs/Projects/pi           → main
/home/lzs/Projects/pi-task-002  → task/002-event-protocol
/home/lzs/Projects/pi-task-003  → task/003-session-storage
```

给 Agent 的提示词必须同时写出任务卡、工作目录和分支名。

### 12.3 并行期间规则

- 每个实现 Agent 只写自己的 worktree；
- 每个任务分支只处理一张任务卡；
- 共享文件由协调者在 `main` 或专门的集成分支处理；
- 不从其他 worktree 复制未提交文件；
- 需要其他任务结果时，通过已提交 commit 交接；
- 合并前检查分支与 `main` 的完整差异；
- worktree 只在任务已集成且确认不再需要后清理。

## 13. 文件所有权与冲突控制

任务卡应列出主要文件所有权。以下文件默认为高冲突文件：

- `doc/plan.md`；
- `doc/tasks/README.md`；
- 根 `package.json`；
- workspace 配置；
- lockfile；
- 共享类型和事件协议；
- 数据库 schema 与迁移；
- CI、构建和 lint 配置。

处理方式：

1. 实现 Agent 在任务卡中描述所需改动。
2. 协调者判断是否需要单独建立共享任务。
3. 协调者统一修改，或指定唯一写入者。
4. 其他 Agent 等共享改动提交后再同步。

如果开始后才发现文件重叠，协调者应暂停其中一个写入者并重新安排顺序。

## 14. Git 提交约定

一个提交应：

- 只包含一个清晰目的；
- 不混入全仓格式化、无关重命名或临时调试文件；
- 已运行与改动相称的验证；
- 提交信息能让审查者理解结果；
- 提交正文引用任务编号。

示例：

```text
feat(runtime): add PI SDK streaming probe

Refs: TASK-001
```

常用类型：`feat`、`fix`、`refactor`、`test`、`docs`、`chore`。

Agent 不得擅自覆盖他人的提交历史、强制推送或回退无法确认来源的改动。

## 15. 交接清单

每次切换前，任务卡至少回答：

- 当前任务编号和状态是什么？
- 目标和验收标准是什么？
- 已经完成什么？
- 还剩什么？
- 修改了哪些文件？
- 做了哪些关键决定，为什么？
- 运行了哪些验证，结果如何？
- 哪些验证还没运行，为什么？
- 是否存在未提交改动？
- 是否有已知缺陷、风险或阻塞？
- 下一位 Agent 应从哪个具体动作开始？
- 当前 Agent 是否已经停止写入？

“代码差不多完成”“继续处理剩余问题”都不是有效交接。下一步应具体到文件、函数、命令或待验证行为。

## 16. 可直接复制的提示词模板

模板中的路径、任务编号和分支名都要替换为真实值。

### 16.1 让额度即将耗尽的 Agent 交接

```text
你当前负责 TASK-NNN。请停止扩大范围，在退出前完成一次可恢复交接：

1. 阅读 AGENTS.md 和当前任务卡，确认范围与验收标准。
2. 停在安全检查点，运行当前阶段能够运行的验证。
3. 更新 doc/tasks/NNN-short-name.md，写清：
   - 已完成和未完成内容；
   - 关键决策及原因；
   - 修改文件；
   - 验证命令和结果；
   - 未提交改动；
   - 已知问题、风险或阻塞；
   - 下一位 Agent 的第一个具体动作。
4. 可以独立成立的改动请提交，并在提交正文写 Refs: TASK-NNN。
5. 不要开始新的子任务。完成后明确说明你已停止写入。
```

### 16.2 让新 Agent 接管未完成任务

```text
请接管 TASK-NNN，工作目录是 /absolute/path，分支是 task/NNN-short-name。

开始前依次阅读：
1. AGENTS.md
2. doc/plan.md 中相关章节
3. doc/tasks/README.md
4. doc/tasks/NNN-short-name.md

然后检查 pwd、当前分支、git status、git diff 和最近提交，核对任务卡里的交接记录。先简短复述目标、范围、验收标准、现有进度和下一步，再从交接点继续。不要重做已完成且已验证的工作，不要修改 /home/lzs/Projects/pi/pi。持续更新同一张任务卡，完成所有验收和验证后再提交审查。
```

### 16.3 分配新的实现任务

```text
你负责实现 TASK-NNN，工作目录是 /absolute/path，分支是 task/NNN-short-name。

先阅读 AGENTS.md、doc/plan.md、doc/tasks/README.md 和当前任务卡。你的写入范围以任务卡为准。开始前检查 Git 状态，并复述目标、范围外事项和验收标准。

实现过程中小步修改，运行任务要求的验证，把进度、决策、验证结果和风险写回任务卡。发现需要修改共享文件时，先记录需求并交给协调者。完成后提交独立改动，提交正文写 Refs: TASK-NNN，并把任务状态更新为 review。
```

### 16.4 分配只读调研任务

```text
你负责 TASK-NNN 的只读调研。请阅读 AGENTS.md、doc/plan.md 和任务卡。允许阅读项目代码、/home/lzs/Projects/pi/pi 中的 PI 源码参考，以及任务明确指定的外部资料。

不要修改实现文件。围绕任务卡的问题输出：
1. 结论；
2. 关键证据和文件位置；
3. 可选方案及取舍；
4. 推荐方案；
5. 对后续实现的接口、测试和风险建议。

将最终结论写入任务卡指定位置，并列出仍未确认的事项。
```

### 16.5 分配代码审查任务

```text
请审查 TASK-NNN 的实现。工作目录是 /absolute/path，目标分支是 task/NNN-short-name。

先阅读 AGENTS.md、任务卡和相关计划，再检查该分支相对 main 的完整差异。重点验证：
- 是否逐项满足验收标准；
- 是否出现范围外改动；
- 正确性、错误处理、并发、安全和兼容性；
- 测试与验证是否覆盖关键行为；
- 文档、类型和实现是否一致。

按严重程度输出问题，注明文件和位置，并说明触发条件与建议修复方向。没有问题时，写明审查范围、验证和剩余风险。除非任务明确授权修复，否则只做审查。
```

### 16.6 分配集成任务

```text
你是 TASK-NNN 的集成者。先阅读 AGENTS.md、任务卡、审查结论，并检查源分支与 main 的差异和 Git 状态。

只有在验收标准完成、必要验证通过、审查问题已解决后才集成。处理冲突时以 doc/plan.md 和已确认的共享协议为准，不要静默改变任务行为。集成后运行受影响范围的验证，更新 doc/tasks/README.md 和任务卡，将状态改为 done，并记录集成提交和剩余风险。
```

### 16.7 让协调者安排多个并行 Agent

```text
请作为协调者组织以下任务并行开发：TASK-AAA、TASK-BBB、TASK-CCC。

先阅读 AGENTS.md、doc/plan.md 和所有相关任务卡，检查依赖、文件重叠和共享配置。只并行安排真正独立的任务。为每个写入者分配独立分支和 worktree，明确工作目录、文件所有权、验收标准和交接要求。共享文件由你统一处理。

持续收集各任务的状态与交接记录。任务进入 review 后安排独立审查；通过后按依赖顺序集成，并更新任务索引。不要让两个运行中的 Agent 写同一个工作区。
```

### 16.8 日常最简接力提示词

```text
接管 TASK-NNN。先读 AGENTS.md、doc/plan.md、doc/tasks/README.md 和任务卡，再检查当前分支、Git 状态、差异与最近提交。根据任务卡的最新交接从下一步继续，完成验收和验证，持续更新任务卡。不得修改 pi/ 参考源码或覆盖不明改动。
```

短提示词只适合任务卡维护良好的情况。如果缺少范围、验收标准或交接信息，应先补齐。

## 17. 完整示例：TASK-001 的顺序接力

### 阶段一：协调者分配

1. 确认任务卡为 `doc/tasks/001-pi-sdk-spike.md`。
2. 确认目标是验证 PI SDK 的最小集成路径。
3. 分配唯一实现 Agent，并给出目录和分支。
4. 把状态从 `backlog` 改成 `in_progress`。

### 阶段二：第一个实现 Agent 工作

1. 阅读规则、计划和任务卡。
2. 检查 PI SDK API 与本地参考源码。
3. 实现最小实验代码。
4. 运行类型检查和实验验证。
5. 持续把结论写入任务卡。

### 阶段三：额度即将耗尽

协调者发送第 16.1 节的交接提示词。旧 Agent 停止新增功能，提交当前实现，写清已验证行为、失败尝试、剩余问题和下一步，然后明确停止写入。

### 阶段四：第二个实现 Agent 接管

协调者发送第 16.2 节的接管提示词。新 Agent 核对任务卡和 Git 状态，从指定下一步继续，完成剩余验收标准，并将任务推进到 `review`。

### 阶段五：审查与集成

1. 审查 Agent 按任务卡逐项检查。
2. 实现 Agent 修复审查问题。
3. 集成者运行最终验证并集成改动。
4. 协调者把任务卡和任务索引更新为 `done`。
5. 如果实验产生架构结论，将其同步到 `doc/plan.md`。

这个过程可以切换任意数量的 Agent。只要每次都保存任务状态，下一个 Agent 就不依赖前一个 Agent 的聊天上下文。

## 18. 节省额度的方法

多 Agent 不会自动节省额度。每个 Agent 都会单独读取上下文和分析代码，边界不清时反而增加消耗。建议：

- 默认顺序接力，只在任务真正独立时并行；
- 把稳定规则写入 `AGENTS.md`，避免每次重复解释；
- 把状态写进任务卡，只给新 Agent 任务编号和入口文件；
- 交接记录结论、证据和下一步，不粘贴大量原始日志；
- 调研任务限定具体问题和输出格式；
- 审查 Agent 读取具体分支差异，不重新研究整个项目；
- 控制任务规模，让单个 Agent 能形成安全检查点；
- 对已验证内容引用命令和提交，不要求无条件重复；
- 只有代码或依赖变化影响原验证时，才扩大回归范围。

## 19. 常见错误与修正

### 19.1 只说“继续上一个 Agent 的工作”

新 Agent 不知道任务、分支、已验证内容和未提交改动。应提供任务编号、目录、分支和任务卡路径，并让它先核对 Git 状态。

### 19.2 两个 Agent 同时写同一目录

文件会互相覆盖，Git 状态也无法说明归属。顺序接力时先停止旧 Agent；并行时创建独立 worktree。

### 19.3 只在聊天中交接

聊天可能无法被下一任务读取，也不会进入版本历史。交接写进任务卡，代码写进提交。

### 19.4 没有验收标准就开始

Agent 容易自行扩展范围，最终无法判断是否完成。应先完成任务卡，再改为 `in_progress`。

### 19.5 所有 Agent 都修改共享文件

会产生高频冲突和不一致决策。共享文件由协调者或明确指定的唯一写入者处理。

### 19.6 交接只描述成功结果

下一位 Agent 会重复失败尝试或忽略未验证假设。应记录失败尝试、未运行验证、风险和具体下一步。

### 19.7 实现结束就标记 `done`

这会跳过审查、集成和最终验证。实现者推进到 `review`，协调者集成后再改成 `done`。

### 19.8 用多个 Agent 处理强依赖任务

后续 Agent 会基于不稳定接口返工。应先完成基础协议或上游任务，再启动依赖任务。

## 20. 快速检查表

旧 Agent 退出前：

- [ ] 不再扩大范围；
- [ ] 当前改动处于安全检查点；
- [ ] 已运行当前阶段适用的验证；
- [ ] 任务卡写明完成、未完成、决策、风险和下一步；
- [ ] 可提交改动已经提交；
- [ ] 未提交改动的原因已经说明；
- [ ] 已明确停止写入。

新 Agent 开始前：

- [ ] 已阅读 `AGENTS.md`；
- [ ] 已阅读相关计划和任务卡；
- [ ] 已确认工作目录和分支；
- [ ] 已检查 Git 状态、差异和最近提交；
- [ ] 已理解现有改动来源；
- [ ] 已确认上一个写入者停止；
- [ ] 已复述目标、边界、验收标准和下一步。

进入审查前：

- [ ] 所有验收标准都有证据；
- [ ] 必要验证已运行并记录；
- [ ] 没有无关文件或调试残留；
- [ ] 文档与实现一致；
- [ ] 风险和限制已记录；
- [ ] 改动已经形成可审查提交。

## 21. 本项目推荐执行方式

本项目是个人练手项目，推荐：

1. 由一个协调者维护 `doc/plan.md`、任务索引和共享协议。
2. 一次只启动一个核心实现任务，用顺序接力应对额度限制。
3. PI SDK 源码阅读交给只读调研角色，结论写入对应任务卡。
4. 核心实现完成后，再使用独立 Agent 审查。
5. 只有两个任务的文件和依赖明确独立时，才建立多个 worktree。
6. 开始并行工作前，先完成仓库初始提交。

这套方式保留了多 Agent 的专业分工，也降低了个人项目中的上下文丢失和合并成本。
