# 项目协作与 Agent 接力流程

## 日常最小流程

本项目默认顺序接力：一张任务卡、一个写入者、一次审查。无需每条命令都创建 Issue，也无需为了角色分工启动多个 Agent。多个 Agent 不会自动节省额度。

```text
定义任务 → 分支实现 → 验证 → review → 用户提交/推送 → PR 审查与合并 → done
```

小修复可归入相关任务；独立的目标才建立新卡。用户明确授权 Agent 提交时，可由 Agent 执行提交。创建任务或实现完成本身不代表获得提交、推送或合并授权。

## 信息位置与优先级

| 位置 | 唯一职责 |
| --- | --- |
| AGENTS.md | 长期规则、路径边界、权限与事实优先级 |
| doc/plan.md | 产品目标、版本边界和里程碑 |
| doc/tasks/NNN-*.md | 详细状态、范围、验证和交接 |
| doc/tasks/README.md | 任务摘要与导航 |
| doc/decisions/ | 已验证行为、架构决定和未决限制 |
| Git 日志和差异 | 实际修改与集成事实 |

优先级与 AGENTS.md 一致：当前用户指令 > AGENTS.md > 计划 > 任务卡 > 代码和其他文档。冲突由集成负责人记录并修正，不静默扩大范围。

仓库已经存在提交。创建 worktree 的通用前提是“有可引用的基准提交”；短期进度记录在任务卡，不写进长期操作规则。

## 任务定义

TASK-NNN 是三位编号，例如 TASK-003。编号不能复用，状态以卡片为准。复制 [模板](tasks/TEMPLATE.md)，填写目标、非目标、输入、允许路径、依赖、验收、验证命令和权限。

任务卡不是 Issue。仅需本地协作时用任务卡即可；要公开讨论需求、跟踪外部 bug 或接受贡献时再创建 GitHub Issue。

当前任务和下一编号从 [索引](tasks/README.md) 查询。共享文件必须指定一个写入者，不能让两个任务同时修改根锁文件或协议。

## 状态与完成条件

| 状态 | 含义 |
| --- | --- |
| backlog | 已定义但未开始 |
| in_progress | 唯一负责人正在工作 |
| blocked | 有明确外部阻塞，记录原因和解除条件 |
| review | 实现可审查，记录验证与剩余问题；尚未全部验收/集成 |
| done | 验收、审查、集成和状态同步均完成 |

代码已经合并也可能因复审重开到 review；必须保留原合并记录，并另建修复任务，不修改历史来掩盖问题。

review 可以交付未提交的完整差异；没有授权时不得为了满足流程自行提交。done 不能只依据测试打印“通过”，每项验收应有证据，未验证的干净安装或真实模型必须明确列出。

## 角色与工作区

- 实现者负责一个任务，更新卡片和索引摘要。
- 集成者管理共享规则、协议、计划和最终状态；用户可以兼任。
- 审查者检查差异和证据，关注失败路径、边界及文档一致性；可以由用户或后续 Agent 承担。
- 角色不等于必须同时启动多个 Agent。只有用户明确要求且任务独立时才并行安排。

顺序接力：旧 Agent 停止后，新 Agent 可复用同一 checkout 和分支。并行写入：不同分支和 worktree，文件边界不能重叠。只读审查不需要创建可写 worktree。

只读参考 `pi/` 不参与安装或编译；没有它也能工作。私有笔记 `doc/internal/` 不进入公开提交。

## 开始工作

先执行：

```bash
pwd
git status --short --branch
git log -5 --oneline
git diff --stat
```

阅读 AGENTS.md、计划相关部分、索引和任务卡。确认旧写入者已停止，理解已有改动。记录任务负责人、分支、基线和范围，再实施。环境安装或升级可以交由用户执行，代码检查仍需报告真实结果。

独占工作区且干净时，任务分支示例：

```bash
git switch -c task/003-project-foundation
```

仅在需要并行时，由集成者创建 worktree，示例：

```bash
git worktree add ../pi-task-NNN -b task/NNN-short-name main
```

执行前将占位符换成索引中的真实任务。不要机械执行示例去创建不存在的任务。

## 验证与交接

1. 运行相关类型检查和测试；尽量不重复没有变化的广泛检查。
2. 检查预期失败是否真的失败，不能只证明正常路径可运行。
3. 填写逐项验收证据，区分模拟、真实模型、现有环境和干净安装。
4. 更新卡片、索引摘要；仅在里程碑或范围改变时改计划。
5. 写清未提交文件、限制和下一动作。未经授权不创建 commit。
6. 到安全检查点后停止写入，再由下一位 Agent 接管。

任务卡引用实际已有的提交 SHA 或 PR。当前未提交就写“无”，集成后再补，不为获得自身 SHA 无限 amend。

## 用户提交与 PR

始终先进入仓库根目录。只暂存当前任务卡列出的路径：

```bash
cd ~/Projects/pi
git diff --check
git status
# git add 后填写本任务的具体路径
git diff --cached --stat
git diff --cached --name-only
# 检查后执行 git commit
```

提交信息示例：`fix(TASK-002): harden SDK checks and align project plan`。不要直接执行含注释或占位符的提交指令。

commit 保存本地历史，push 发布任务分支，PR 用于检查与合并。PR 说明最终问题、修复行为、验证和限制；不复制内部研究笔记。用户操作完成后，集成者核对 SHA、更新任务状态，任务才进入 done。

## 可直接复制的接力提示词

### 接管任务

```text
接管 TASK-NNN。先读 AGENTS.md、doc/plan.md 相关内容、doc/tasks/README.md 和任务卡。
检查当前分支、Git 状态、差异与最近提交，确认旧 Agent 已停止写入。
从任务卡的下一步继续，只修改允许路径，不重做已验证工作。
持续更新任务卡和索引；未授权时不提交或推送。
```

### 请求交接

```text
请在安全检查点完成 TASK-NNN 的交接，不开始新范围。
运行当前必要检查，写清已完成、未完成、关键决策、修改路径、验证、风险、
未提交改动和下一位 Agent 的第一个动作。没有提交授权时保留完整差异。
同步任务索引，并明确说明已停止写入。
```

### 请求审查

```text
审查 TASK-NNN。先读规则、任务卡、相关计划和 ADR，再检查实际差异。
核对失败路径、配置隔离、成本/取消、协议和逐项验收证据。
按严重性报告文件位置、触发条件与建议，不把模拟验证当真实模型验证。
除非明确授权修复，否则只做审查。
```

## 合并后的状态同步

- 确认远端和本地主分支的实际提交，不只看旧的 origin/main 缓存。
- 任务卡记录实现提交、PR 和集成提交；勾选有证据的验收项。
- 有验收缺口时保留 review 并明确后补任务。
- 索引状态同步，计划更新完成的里程碑。
- 分支/worktree 清理由用户或集成者在确认无未保存内容后执行。
