## 项目目标

使用 PI SDK、Node.js 和 TypeScript 构建一个 Agent 应用，并参考成熟 Agent 工作台的架构设计。项目是个人练手项目，不要求先找到真实用户，也不以商业化或生产部署为验收条件；重点是完成一个可运行、可评测、可解释的 Agent 工程闭环，并形成适合技术面试讨论的项目成果。

项目成果目标的优先级暂调整为：可运行的完整原型 > 求职项目 > 开源影响力 > Agent 基础设施学习。后续范围取舍优先保证一个完整、可复现、可评测的工作流，再把工程能力沉淀为简历与开源成果。

项目定位为基于 TypeScript + PI SDK 的 Agent 工作台实现，不追求任何外部框架源码、内部结构或 API 的严格兼容。项目使用一个贯穿各版本的垂直案例作为演示与评测场景，以验证新增能力是否改善任务结果。当前候选场景是招投标文件变更与响应核查，但尚未最终确定。由于项目是练手项目，第一版可以使用公开资料和合成数据，不把真实用户接入作为前置条件。

这个项目的差异化不能只是把其他 Agent 框架的后端翻译成 TypeScript。关于速度、成本、可靠性或部署简便性的判断，都必须通过实际测量支持。

## 项目价值

- PI 已经提供模型调用、工具执行、事件流、会话状态和资源加载等基础能力。
- 项目可以把重点放在业务层能力：可恢复任务、受控委派、沙箱工具、证据追踪和可用的 Web 工作台。
- 垂直业务流程能够提供具体输入、输出、失败场景和评测标准。
- 可复用的 TypeScript 组件可能帮助其他开发者在 Node.js 应用中嵌入 PI。

## 当前产品假设

用户在 Web 工作台中发起一个长时间任务。基于 PI 的主 Agent 检查上传文件、调用领域工具、委派受限子任务、记录证据并生成可审阅的产物。浏览器断开后任务继续运行，Worker 重启后可以安全恢复。

贯穿各版本的默认场景是 GitHub 开源项目技术尽调与复现：

1. 输入一个公开 GitHub 仓库地址和调研目标。
2. 获取仓库代码、README、文档、提交信息和公开的项目元数据。
3. 分析项目定位、架构、核心模块、依赖、启动方式和已知限制。
4. 在受控环境中安装、运行并验证最小示例。
5. 生成带文件路径、提交版本、命令输出和网页来源的技术尽调及复现报告。
6. 允许用户追问、修正结论，并在后续会话中继续任务。

该场景使用公开数据，能够覆盖 Agent 工作台的调研、编码、文件操作、沙箱、子 Agent、记忆、Skills、长任务和产物管理能力。

## v1.0 目标范围

1. Web 工作台：对话、任务状态、工具时间线和产物预览。
2. 一个基于 PI SDK 构建的主 Agent，并使用明确的工具白名单。
3. 最多两个并发子任务；每个子任务具有独立上下文、取消和超时能力。
4. 持久化任务阶段和输出；任务重启后从已完成阶段安全恢复。
5. 每个任务使用独立工作区；只有确实需要执行任意代码的工具才使用 Docker 隔离。
6. 一个完整的 GitHub 项目技术尽调与复现流程，以及可复现的评测数据集。

### v0.1：单 Agent 最小闭环

- 参考成熟 Agent 工作台的主 Agent、Gateway API 和流式运行机制。
- PI SDK 会话接入。
- 自定义工具注册与结构化结果。
- Node.js API 和基础 Web 工作台。

## 需求访谈默认决策

以下答案作为后续设计和实现的默认约束。只有出现原型证据或用户明确提出变更时才调整。

### 1. 能力与兼容边界

- 聚焦用户可观察到的核心能力和关键任务流程，不复制任何特定框架的内部结构。
- 不承诺外部 Agent 框架的 API、配置文件、数据库结构或扩展接口兼容。
- 对照同类 Agent 工作台的相同能力记录行为差异和取舍。

### 2. 支持环境与部署方式

- v0.1 仅支持本地 Linux 单用户运行。
- 使用 Node.js 活跃 LTS 版本和 npm workspaces。
- Web、API 和 Agent Worker 在同一台机器运行，由一条开发命令统一启动。
- v0.1 不做登录、多租户、公网部署、Kubernetes、Helm 或跨平台保证。
- v0.4 引入 Docker 后，再把容器作为正式运行依赖。

### 3. 仓库结构与进程边界

```text
apps/
  web/            Next.js 工作台
  server/         Fastify REST/SSE API
  worker/         PI Agent 任务执行入口
packages/
  agent-runtime/  PI SDK 适配层
  protocol/       API、事件和产物数据结构
  tools/          GitHub、仓库和文件工具
  storage/        任务、事件、检查点和产物索引
  evals/          固定样例、评分器和评测命令
```

- 使用 TypeScript strict 模式和 ESM。
- v0.1 保持逻辑模块分离，但允许 Server 与 Worker 在一个进程内运行。
- v0.2 再拆分独立 Worker，并使用持久化任务认领机制，不在 v0.1 引入消息队列。

### 4. v0.1 输入与 GitHub 访问

- 只接受公开 GitHub HTTPS 仓库地址和可选的分支、标签或提交 SHA。
- 实际运行前将输入解析为不可变提交 SHA，报告和缓存都以该 SHA 标识。
- 使用浅克隆获取源码，使用 GitHub REST API 获取公开元数据；Token 可选，仅用于提高限额。
- 不做 GitHub OAuth、私有仓库、Issue 写入、PR 创建或其他外部写操作。
- 限制仓库大小、文件数量和单文件大小；拒绝路径逃逸，并谨慎处理符号链接。

### 5. PI SDK 集成方式

- 使用 `@earendil-works/pi-coding-agent` 的会话 API 作为主要入口，不直接重写模型和工具循环。
- 在 `packages/agent-runtime` 中建立薄适配层，隔离 PI SDK 版本变化。
- 模型选择、认证和提供商能力尽量复用 PI 的机制，不再建立一套平行的模型抽象。
- v0.1 只向 Agent 暴露只读仓库工具，不暴露 shell、写文件或通用网络工具。

### 6. 状态、事件和流式协议

- 所有运行事件使用带版本号的统一事件封装，至少包含 `eventId`、`runId`、`type`、`timestamp` 和结构化 payload。
- 浏览器通过 SSE 获取事件；客户端使用最后事件 ID 重连。
- 事件按运行追加写入，不原地修改历史事件。
- v0.1 可以使用内存状态和本地产物目录；v0.2 使用 SQLite WAL、数据库迁移和任务检查点。
- PostgreSQL 和外部队列只有在 SQLite 的并发或部署约束被实际证明后再引入。

### 7. 报告、证据和产物格式

- 每次运行至少生成 `report.md`、`report.json`、`manifest.json` 和结构化事件日志。
- 报告必须覆盖：项目定位、架构、核心模块、入口、依赖、启动方式、测试方式、风险、未知项和复现建议。
- 事实结论必须关联仓库路径、行号范围和提交 SHA，或关联带访问时间的网页 URL。
- 明确区分已验证事实、合理推断和未知项。
- 确定性校验器验证引用路径存在、行号有效、SHA 一致和 JSON Schema 合法；校验失败的报告不能标记为完成。

### 8. v0.1 完成标准

- 固定样例能够从仓库 URL 完成到最终报告，不需要人工修改文件或状态。
- 连续三次运行都不出现未处理异常，并产生符合 Schema 的全部产物。
- 100% 的结构化引用能够解析到固定提交中的有效文件和行号，网页引用能够解析为有效 URL。
- 在人工维护的必答事实清单上，初始目标召回率不低于 80%。
- Web 工作台能够按顺序显示消息、工具调用、进度、错误和最终产物。
- 工具清单中不存在命令执行、依赖安装、仓库代码运行或外部写入能力。

### 9. 固定评测集

- 一个项目自带的合成 TypeScript fixture，用于确定性错误和边界测试。
- `sindresorhus/slugify`，代表小型、结构清晰的包。
- `honojs/hono`，代表中型 TypeScript 框架或多包项目。
- `earendil-works/pi`，代表大型 Agent monorepo。
- 所有第三方样例固定到明确提交 SHA，在评测时克隆，不把第三方完整源码提交进本项目。
- 本项目只保存许可信息、事实清单、期望结构和评分规则。

### 10. 子 Agent 规则

- v0.3 最多允许三个并发子 Agent，作为受控并发能力的验证上限。
- 每个子 Agent 使用独立 PI 会话、明确任务、工具白名单、时间预算和 Token 预算。
- 子 Agent 返回结构化结果和证据，不直接修改主 Agent 的结论。
- 主 Agent 负责去重、冲突标记和最终合并；取消请求向所有子任务传播。
- 必须与单 Agent 基线比较质量、耗时和成本，无法证明收益时默认关闭委派。

### 11. 沙箱与安全边界

- v0.1 只读克隆和分析，不执行目标仓库代码。
- v0.4 使用一次性、非特权 Docker 容器；不挂载 Docker socket，不共享宿主凭据。
- 限制 CPU、内存、PID、磁盘和运行时间，工作区使用专用挂载。
- 网络默认关闭；只有安装依赖确实需要时才按任务或域名显式开启。
- 外部写操作默认不存在；未来加入时必须具备预览、人工确认、幂等键和审计事件。

### 12. 记忆、RAG、Skills 与 MCP

- 区分运行检查点、线程上下文、项目知识和用户偏好，不能把它们混为一个记忆集合。
- v0.5 首先实现带来源的项目知识和显式保存，不自动把所有对话写入全局长期记忆。
- RAG 只负责候选证据召回，最终结论仍必须引用原始文件或网页。
- Skills 使用可版本化的本地 Markdown/TypeScript 资源；MCP 第一版只支持本地显式配置。
- 不在 v1.0 之前开发 Skills 市场、远程安装中心或自动信任第三方工具。

### 13. Web 工作台范围

- 包含任务输入、运行列表、对话流、工具时间线、来源查看器、产物预览以及取消/重试控制。
- UI 展示结构化事件，不解析终端日志来推测状态。
- v0.1 不追求复杂 Agent 工作台的视觉设计，也不做移动端、即时通信渠道、多人协作或主题系统。

### 14. 测试、模型与成本

- 单元和集成测试默认使用假模型或录制事件，不调用付费模型。
- 在线模型评测单独运行，要求显式环境变量、模型名称、Token 上限和成本上限。
- v0.1 选择一个经过验证的主模型形成基线；多模型兼容性在基础流程稳定后再扩展。
- 每次评测记录模型标识、提示版本、数据集版本、提交 SHA、耗时、Token 和估算成本。

### 15. 开源、命名和许可证

- 项目独立实现，不使用其他项目的名称、Logo 或声称兼容的表述；README 只说明 PI SDK 依赖和本项目的独立定位。
- 暂用工作名 `PI Agent Workbench`，正式发布前再检查 GitHub、npm 和域名冲突。
- 默认使用 MIT 许可证；如果后续复制第三方代码，则在合入前逐项审查许可证和归属要求。

## 第一版明确不做的内容

- 外部 Agent 平台的完整功能对齐或 API 兼容。
- 替代所有 Agent 框架的通用平台。
- 无限制的自主执行。
- Skills 或 Agent 市场。
- v1.0 同时维护多个默认演示场景。
- 没有证据支持的生产可用、性能或安全性声明。

以上边界是初步版本，会在需求探索阶段继续修订。

## 建议的技术架构

```text
Next.js 工作台
        |
   REST 和 SSE
        |
Node.js API -------- SQLite
        |             任务、事件、检查点
        |
PI Agent Worker
        |
领域工具 -- 子任务委派 -- Docker 沙箱
        |
证据、报告和生成的项目产物
```

### 各模块职责

- 工作台：提交任务、重新连接事件流、查看证据、审阅产物并提供人工决策。
- API：任务生命周期、文件上传、产物访问和事件流；v1.0 之前不承担多用户认证。
- Worker：创建 PI 会话、执行阶段、控制预算和取消、对持久化结果建立检查点。
- 任务存储：保存状态转换、工具事件、检查点和幂等键。
- 沙箱：工具需要执行命令或代码时，隔离文件和运行环境。
- 领域层：确定性解析器、校验器、检索工具和报告数据结构。

## 交付阶段

### 阶段 0：需求探索与决策记录

交付物：

- 定义 GitHub 项目技术尽调与复现主流程及其边界。

### 阶段 1：PI SDK 技术验证

交付物：

- 一个最小 Node.js 进程能够创建 PI 会话。
- 一个自定义工具能够运行并输出结构化事件。
- 记录取消、超时和错误行为。
- 记录哪些 PI API 足够稳定，可以用于正式架构。

退出条件：可重复的演示证明所选择的 PI 集成路径可行。

### 阶段 2：单 Agent 技术尽调闭环

交付物：

- 通过 API 提交一个任务。
- 处理具有代表性的输入文件。
- 将进度流式展示到工作台。
- 生成一个带证据关联的产物。

## 方案比较

### 直接沿用现成框架内部实现

- 优点：功能映射直接，容易逐项比较。
- 缺点：会被特定框架的内部设计约束，PI SDK 和 TypeScript 的价值难以体现。
- 结论：不采用，不追求外部系统源码、内部结构或 API 兼容。

### 只做通用 Agent 框架

- 优点：看起来适用范围广。
- 缺点：缺乏固定任务和评测基线，容易只完成基础设施演示。
- 结论：不采用，必须用 GitHub 项目技术尽调与复现贯穿版本。

### 只做单一垂直应用

- 优点：产品范围清楚，容易设计界面。
- 缺点：无法系统练习 Agent 工作台的运行时、子 Agent、沙箱和记忆能力。
- 结论：不作为项目本体；垂直任务只承担默认演示与评测角色。

### 独立实现 Agent 工作台核心能力并使用固定场景验证

- 优点：兼顾 Agent 基础设施学习、可运行成果、持续评测和开源解释力。
- 缺点：路线较长，需要严格按照版本边界推进。
- 结论：采用。
